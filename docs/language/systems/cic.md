# CIC — Calculus of Inductive Constructions

`language/src/type_theory/cic/`

CIC is the primary type system. It supports dependent types, inductive type definitions, and interactive proof construction via tactics. It is the default system and the one the standard library targets.

## Term Grammar

```rust
pub enum CicTerm {
    Sort(String),                                  // TYPE, PROP
    Variable(String, i32),                         // x, De Bruijn index
    Abstraction(String, Box<CicTerm>, Box<CicTerm>), // λx:A. b
    Product(String, Box<CicTerm>, Box<CicTerm>),     // Πx:A. B  (∀x:A. B)
    Application(Box<CicTerm>, Box<CicTerm>),          // f a  (binary)
    Match(Box<CicTerm>, Vec<(CicTerm, CicTerm)>),     // match t with …
    Let(String, Box<Option<CicTerm>>, Box<CicTerm>, Box<CicTerm>), // let x := b in s
    Meta(i32),                                     // ?[n]  metavariable
}
```

`Term = Type = Exp` in CIC — types are terms. There is no syntactic distinction between "a term" and "a type"; the universe hierarchy is enforced by the kernel rules.

Surface syntax for function/constructor application is parenthesized and comma-separated — `f(a, b, c)`, `le(z, n)`, `cons(h, l)` — not space-juxtaposition. `elaborate_application` (`cic/elaboration.rs`) folds the argument list into nested binary `Application` nodes left-to-right, so `f(a, b, c)` elaborates to `((f a) b) c`.

### Sorts

Two sorts are built in:
- `TYPE` — the sort of computational types (e.g. `Nat: TYPE`)
- `PROP` — the sort of propositions (e.g. `True: PROP`, `Eq(Nat, z, z): PROP`)

Both are axiomatically given type `TYPE` in the default environment.

### Variables and De Bruijn Indices

Variables carry both a name (for display) and a De Bruijn index. The index `-1` (`GLOBAL_INDEX`) marks globally defined names. The index `-2` (`PLACEHOLDER_DBI`) is a temporary marker during elaboration. Bound variables use non-negative indices starting at `0` (`FIRST_INDEX`).

### Metavariables

`Meta(i32)` represents an unsolved implicit argument, elaborated from `Inferator()` (`_`) in the source. The `Refiner` implementation collects unification obligations on metas via `term_collect_unifications`/`type_collect_unifications`, solves them into a `Substitution<CicTerm>` via `solve_unifications`, and applies the result back into terms via `term_apply_unifier`/`type_apply_unifier` (built on `substitute_meta`) — see [Unification](#unification).

## Type Checking Rules

Type checking is implemented in `cic.rs` by delegating to helpers from `commons/type_check.rs` and CIC-specific functions.

### Sort checking (`type_check_sort`)

`TYPE` and `PROP` are in context with type `TYPE`. Other sort names are looked up.

### Variable (`type_check_variable`)

Standard VAR rule: look up `x` in `Γ`, return its type.

### Abstraction

`i_type_check_abstraction` (unification-aware variant, `commons/type_check.rs`): type checks the domain `A`, extends the context with `x:A`, type checks the body `b` to get `B`, collects unification constraints from both `A` and `B` (`type_collect_unifications`/`term_collect_unifications`), solves them via `solve_unifications`, applies the resulting substitution to `A` and `B` (`type_apply_unifier`), and constructs `Product(x, A, B)` as the type.

### Product / Universal Quantification

`type_check_fo_universal`: type checks `A`, extends context with `x:A`, type checks `B`. Returns `B`'s sort. This handles both `Πx:A.B` (dependent function space) and `∀x:A.P(x)` (universal propositions).

### Application

`i_type_check_application` (unification + dependent types, `commons/type_check.rs`): type checks the argument and the function, then — once the function's type unpacks to `Product(x, A, B)` — collects unification constraints from the whole (re-assembled) application term via `term_collect_unifications` (this already includes the obligation `A ≐ arg_type`, generated by `cic_collect_unifications`'s `Application` case), solves them via `solve_unifications`, substitutes the argument into the codomain (`B[arg/x]`) for dependent types, and applies the resulting substitution to the codomain (`type_apply_unifier`).

### Match

`type_check_match` in `cic/type_check.rs`: checks the matched term, recovers the inductive type name from the head of its (applied) type, and looks up its registered constructors via `environment.get_constructors_for`. For each branch it type checks the pattern against the matching constructor's type (`type_check_pattern`), unifies the pattern's reconstructed type against the matched term's type (`Cic::terms_unify`), binds the pattern's variables in the branch body (`type_constr_vars`), and unifies all branch body types against each other (`Cic::terms_unify`, not plain equality). It errors if any constructor of the inductive type is left uncovered by the branches (exhaustiveness check).

### Let

`type_check_let`: type checks the body, verifies the declared type matches, adds the binding to the environment scoped to the closure, and returns the type of the scope expression.

### Inductive Types

`type_check_inductive` in `cic/type_check.rs`: validates the parameter types and arity, then type checks each constructor type with the type name and parameters in scope, rejecting constructors whose recursive argument occurs non-positively (`check_positivity`). On success it calls `evaluate_inductive` (`cic/evaluation.rs`), which adds the type name, every constructor name, and a generated eliminator `e_<type_name>` (`inductive_eliminator`, following Dybjer's *Inductive Families*) to the environment's context, and records the constructor list for the type in `environment.constructor_store` via `add_constructor_store` (read back by `type_check_match`'s exhaustiveness check).

## Reduction

`one_step_reduction` in `cic/evaluation.rs` dispatches only on `Variable`, `Application`, `Let` and `Match`; every other term (`Sort`, `Product`, `Abstraction`, `Meta`) is returned unchanged, so reduction never descends under an un-applied `Abstraction`/`Product` binder:
- **δ-reduction** (`reduce_variable`): a variable with a definition in `deltas` reduces to its body, otherwise it's a constant and is returned as-is.
- **β-reduction** (`reduce_application`): both the function and the argument are first fully normalized (`Cic::normalize_term`); if the normalized function is an `Abstraction(x, _, body)`, the result is `body[x := normalized_arg]`, otherwise the application is rebuilt from the normalized parts.
- **let-reduction** (`reduce_let`): the bound term is fully normalized, then substituted for the variable in the scope (`scope[x := normalized_body]`).
- **match-reduction** (`reduce_match`): the scrutinee is fully normalized and matched structurally, in branch order, against each pattern (`matches_pattern`, which compares the applied head and arity); on the first match every pattern variable is substituted with the corresponding argument taken from the scrutinee (`substitute_pattern_variables`/`substitute_pattern_arg`), recursing so that variables nested inside constructor sub-patterns (e.g. the `nn` in `s(nn)`) are bound too, not just the top-level ones. A scrutinee that normalizes to something not headed by any of the branches' constructors - an open variable, as happens throughout an inductive proof's step case - leaves the `match` as its own normal form rather than being an error.

- **ι-reduction of eliminators** (`try_reduce_eliminator_application`): a fully applied `e_<Type>(params.., motive, case_1..case_k, indices.., instance)` whose `instance` is a concrete constructor application computes to the matching case, applied to that constructor's arguments with an induction hypothesis (the same eliminator re-applied to the sub-term) inserted after each recursive one. Indexed families are handled: the index count is recovered from the application's arity, and a recursive occurrence's hypothesis is rebuilt with that occurrence's own indices. A scrutinee that isn't constructor-headed leaves the application stuck, which is the normal situation inside an inductive proof's step case.

Reduction also descends into `Product`/`Abstraction` domains and bodies, one step at a time, so a redex embedded under a binder - eg a motive applied to a bound variable, exactly what an eliminator's generated types produce - is reduced too. Without that, two Pi-types equal only up to an under-binder redex are never recognized as such, since unification normalizes both sides before comparing.

`generic_term_normalization` from `commons/evaluation.rs` drives the fixed-point iteration: apply `one_step_reduction` repeatedly until the term is unchanged.

## Elaboration

`cic/elaboration.rs` maps `Expression` → `CicTerm` and `Statement` → `Schedule<Cic>`.

Notable mappings:
- `Arrow(A, B)` → `Product("_", A, B)` (non-dependent product with a dummy variable name)
- `Inferator()` → `Meta(fresh_index)` (allocates a new metavariable from a global counter)
- `Application(f, [a, b, c])` (surface `f(a, b, c)`) → nested binary `Application`s, left-folded: `((f a) b) c`
- `Inductive(name, params, ariety, constructors)` → a single `InductiveDef` statement carrying the elaborated parameters, arity, and the full `(constructor_name, constructor_type)` list; constructors are no longer elaborated as separate `Axiom` nodes
- `Fun(name, args, out_type, body, is_rec)` → elaborates straight to a `CicStm::Fun` node with the body left un-wrapped; the nested `Abstraction`s per argument are only built later, at **evaluation** time, by `evaluate_fun`'s η-expansion (`eta_expand`, `commons/utils.rs`) over the stored substitution

## Interactive Proofs

CIC implements the `Interactive` trait. Tactic checking is in `cic/tactics.rs`.

### Proof hole and empty target

- `proof_hole()` returns `Sort("THIS_IS_A_PARTIAL_PROOF_HOLE")`
- `empty_target()` returns `Sort("THIS_IS_AN_EMPTY_TERMINATION_PROOF_TARGET")`

These sentinel values mark incomplete proofs during tactic construction.

### `type_check_tactic`

Each tactic transforms the `(partial_proof, [subgoals])` pair. `partial_proof` is rebuilt via `swap_proof_hole` (`cic_utils.rs`), which walks down any `Abstraction`s introduced by earlier `Intro`s and replaces the innermost proof-hole sentinel with the new (possibly still incomplete) proof term:

| Tactic | Effect |
|--------|--------|
| `Begin` | Syntax marker for the start of a tactic proof; filtered out by the parser before elaboration, never reaches `type_check_tactic` |
| `Exact(e)` | Type checks `e`, normalizes both its type and the target, and unifies them (`Cic::types_unify`); closes the current goal with `e` |
| `Intro(x, T)` | Requires target `Πx:A.B` with `T` compatible with `A` (`Cic::base_type_equality`); adds `x:T` to the context, wraps the proof as `λx:T. □`, and marks every occurrence of `x` in the codomain as a constant (`mark_as_constant`) before making it the new subgoal `B` |
| `Apply(f)` | Type checks `f`, unifies the target against the innermost return type of `f`'s type (`Cic::type_unify`); on success wraps the proof as `f(□)` and returns one subgoal per premise (`get_arg_types` of `f`'s type) |
| `Qed` | Syntax marker for the end of a tactic proof; filtered out by the parser before elaboration, never reaches `type_check_tactic` |

## Unification

CIC implements both `Refiner` and `TypeInference`. Every entry point returns `Result<_, LofError>` (`UnificationFailure`, `OccursCheckCyclic`, `OccursCheckInTerm`, `ConflictingSubstitution`, …), not the old `Result<_, String>`/`bool` conventions.

The `Refiner` flow is split into three explicit phases (`cic/unification.rs`), rather than accumulating constraints in the environment as type checking proceeds:

1. **Collect** — `cic_collect_unifications(term, environment) -> Result<Vec<(CicTerm, CicTerm)>, LofError>` backs both `term_collect_unifications` and `type_collect_unifications` (`Term = Type` in CIC) and walks `term` for unification obligations. It recurses into `Abstraction`/`Product`'s domain and (context-extended via `environment.with_local_assumption`) body/codomain, into `Let`'s type/body/scope, and into `Match`'s scrutinee and every branch's pattern/body — so binders are properly scoped for the recursive calls. `Application(fun, arg)` is the actual source of constraints: besides recursing into `fun` and `arg`, it emits the pair `(first argument type of fun's type, type of arg)`.
2. **Solve** — `cic_solve_unifications(constraints, environment) -> Result<Substitution<CicTerm>, LofError>` normalizes both sides of every constraint (`Cic::normalize_term`) and hands them to the generic constraint solver `ucs` (`commons/unification.rs`), parameterized with CIC's `is_substitutable`, `structurally_equal`, `explode` and `occurs` callbacks. `cic_so_unification(term1, term2)` runs the same solver without prior normalization, for callers that don't need reduction first (`base_term_equality`/`base_type_equality`, `TypeInference::type_unify`).
3. **Apply** — `cic_apply_unifier(exp, substitution) -> CicTerm` backs both `term_apply_unifier` and `type_apply_unifier`, folding `substitute_meta` over every metavariable index solved by the substitution.

`terms_unify`/`types_unify` solve a single `(term1, term2)` constraint via `cic_solve_unifications`, discard the substitution, and return `Result<(), LofError>`.

`structurally_equal` is CIC's "same shape up to metavariables" check: two `Sort`s or two `Meta`s are always equal; a `Meta` is equal to any `Variable` whose De Bruijn index is `GLOBAL_INDEX` (letting an unsolved implicit stand in for a not-yet-elaborated type/constant name); two `Variable`s are equal if they share a De Bruijn index (and, if constant, the same name); `Abstraction`, `Product`, `Application`, `Let` and `Match` recurse structurally into their sub-terms/branches. `explode` returns those same sub-terms as the pairs the generic solver should unify once two terms are found structurally equal but not syntactically identical (e.g. the domains/bodies of two `Product`s).
